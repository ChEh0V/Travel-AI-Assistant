# Диалоги и контракты

## Текущая реализация

HTTP API чата отсутствует. [app.js](../app/app.js) вызывает `getReply(messages, context)` из [planner.js](../app/planner.js), а затем применяет действие к локальному состоянию. Подбор города и отдельные действия сборов обрабатываются дополнительной логикой интерфейса.

## Локальный контракт

```text
messages: массив { role: "user" | "assistant", content: string, ... }
context: состояние текущей поездки (city, days, plan, interests, ...)
getReply(messages, context)
  → Promise<{ reply: string, action: string | null, city: string | null }>
```

Последнее сообщение должно содержать непустой вопрос. `city` — ключ из `DESTINATIONS`, а не произвольный адрес. Действия: `city`, `free`, `slow`, `walks`, `instagram`, `rebuild` или `null`. `reply` — обычный текст, выводимый через `textContent`. При действии перестроения UI формирует текст по обновлённому плану. Возвращаемые значения не являются результатом BM25 или LLM.

## Жизненный цикл

1. Пользователь создаёт диалог; пустая поездка не добавляется в архив автоматически.
2. Отправка добавляет сообщение, включает состояние ожидания и вызывает обработчик.
3. Уточнения используют текущий город, длительность, интересы и закреплённые места.
4. Ответ, план и связанные данные сохраняются в браузере.
5. Переключение восстанавливает всю поездку, сохраняя порядок карточек.
6. Удаление маршрута очищает план; удаление поездки удаляет всю запись. Исторические сообщения при удалении только маршрута остаются.

## Проект будущей интеграции — не реализован

Планируется серверный `POST /api/chat`: запрос содержит сообщения и явный контекст поездки; ответ — текст, статус достаточности данных и идентификаторы использованных фрагментов. Конкретная JSON-схема, коды ошибок, ограничения длины и стратегия передачи истории должны быть согласованы отдельным изменением перед разработкой сервера.

Адаптер заменит подготовленный ответ вызовом сервера. Сервер отвечает за BM25, контекст для LLM и ключ провайдера. UI отвечает за ожидание, повторную попытку и отображение ошибки. Текст модели не исполняется как HTML и не превращается автоматически в произвольные внешние ссылки.

До подключения нужны контрактные проверки: успешный ответ, отсутствие данных, неправильный запрос, таймаут, ошибка провайдера, отсутствие ключа в клиенте. Неудачный запрос не должен уничтожать текущую поездку. Потоковая выдача, авторизация и многопользовательская синхронизация пока не приняты как обязательные требования.
